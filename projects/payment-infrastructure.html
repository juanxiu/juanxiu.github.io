실시간 결제 서비스

AWS 인프라 설계 및 CI/CD 배포 자동화

2025.03 — 2025.12백엔드 개발 · 클라우드 인프라 구축

실시간 결제 서비스의 백엔드 개발과 클라우드 인프라 구축을 담당했습니다. 제한된 자원에서 서비스 실행 환경을 구성하고, 장애와 배포 중단에 대비하는 데 초점을 맞췄습니다. 블루그린 방식의 무중단 배포와 CI/CD 파이프라인으로 배포 시간을 30분에서 10분으로 단축했습니다.

AWSDockerCI/CDAmazon SQS
프로젝트 개요설계 목표클라우드 아키텍처핵심 설계CI/CD 파이프라인과 무중단 배포Redis를 이용한 푸시 알림 비동기 처리

프로젝트 개요

AWS·GCP 기반 멀티클라우드 환경에서 AWS 인프라 구축과 배포 자동화를 담당했습니다. 제한된 자원을 효율적으로 활용하면서 서비스 가용성을 확보하고, 요청량 변화에 대응할 수 있는 확장성도 함께 고려했습니다.

설계 배경과 요구사항

  • 장애 대응: 운영자가 상시 대응하기 어려워, 장애 발생 시 수동 조치를 기다리지 않고 복구할 수 있어야 했습니다.
  • 서비스 확대: 교내로 확대되는 상황을 고려해, 사전에 확정하기 어려운 요청량에 대응할 수 있어야 했습니다.
  • 접근 보안: 외부에서 결제 서비스를 이용하되, 데이터베이스에 대한 직접 접근은 제한해야 했습니다.
  • 수집 연계: DB 적재 작업이 일시 중단되어도 수집 결과를 보관하고, 처리 재개 후 반영할 수 있어야 했습니다.

설계 목표

구분목표설계 방안
고가용성단일 EC2 또는 Primary DB 장애 시 결제 서비스 복구 목표 시간(RTO) 5분 이내다중 AZ 배포와 자동 장애 조치
확장성요청량 변화에 따른 처리 용량 조정EC2 Auto Scaling
접근 보안데이터베이스의 인터넷 직접 노출 차단프라이빗 서브넷과 보안 그룹
디커플링적재 작업이 중단되어도 수집 결과 보관Amazon SQS로 수집과 적재 분리

클라우드 아키텍처

  • 결제 요청 처리: 클라이언트 → ALB → 프라이빗 EC2 → RDS
  • 카드 데이터 적재: Cloud Run → Amazon SQS → EC2의 적재 작업 → RDS

핵심 설계

다중 AZ 배포(Multi-AZ)

단일 EC2 장애와 Primary DB 장애를 각각 발생시킨 복구 테스트에서 결제 서비스의 RTO 5분 이내를 달성했습니다.

결제 서비스는 장애 발생 시 신속한 복구가 필요했지만, 운영자가 서비스 이용 시간 동안 상시 대응하기는 어려웠습니다. 수동 조치를 기다리는 시간을 줄이기 위해 고가용성(HA) 구조를 설계했습니다.

EC2를 서로 다른 가용영역에 배치하고, ALB 헬스 체크로 인스턴스 상태를 확인하도록 구성했습니다. RDS는 Multi-AZ DB 인스턴스 배포를 적용해 다른 가용영역의 Standby DB에 데이터를 동기 복제하고, Primary DB 장애 시 자동 장애 조치(Failover)를 수행하도록 했습니다.

요청량에 따른 자동 확장

학과 단위 서비스가 교내로 확대되는 상황을 고려해, 요청량 변화에 따라 처리 용량을 조정할 수 있도록 설계했습니다. 제한된 예산을 고려하면서 필요한 용량을 확보할 수 있도록 EC2 Auto Scaling 기반의 확장 구조를 구성했습니다.

네트워크 접근 제어

외부 요청은 퍼블릭 서브넷의 ALB에서 받아 프라이빗 서브넷의 애플리케이션으로 전달합니다. RDS도 프라이빗 서브넷에 배치하고, 보안 그룹으로 애플리케이션에서 필요한 통신만 허용해 인터넷에 직접 노출되지 않도록 설계했습니다.

Amazon SQS 기반 디커플링

수집 서비스와 DB 적재 작업 사이에 Amazon SQS를 두어 두 작업을 디커플링하는 구조를 설계했습니다. 적재 작업이 일시 중단되어도 수집 결과를 큐에 보관하고, 처리 재개 후 RDS에 반영하도록 구성합니다.

DB 반영에 성공한 메시지만 큐에서 삭제하고, 재전달된 메시지는 카드별 수집 ID를 기준으로 중복 반영 여부를 확인하도록 설계합니다.

CI/CD 파이프라인과 무중단 배포

빌드 환경 분리

  • 문제: 운영 EC2에서 빌드 중 메모리 부족 발생
  • 해결: 빌드를 CodeBuild로 분리하고, 운영 EC2에서는 완성된 컨테이너 이미지만 실행

빌드와 배포 자동화

GitHub Actions로 파이프라인을 실행하고, CodeBuild에서 빌드한 결과를 CodeDeploy로 배포하도록 자동화했습니다. 서비스별 Dockerfile로 컨테이너 이미지를 정의하고, Docker Compose로 실행 설정을 관리했습니다.

블루그린 배포

배포로 인한 서비스 중단시간(다운타임)을 최소화하기 위해 블루그린 무중단 배포를 적용했습니다. Green 환경에 새 버전을 배포하고, 헬스 체크 통과를 확인한 뒤 로드밸런서의 트래픽을 전환했습니다.

결과배포 시간 30분 → 10분

Redis를 이용한 푸시 알림 비동기 처리

푸시 전송을 기다리지 않고 결제 결과 응답

결제 서비스는 결제 결과와 알림 작업을 하나의 DB 트랜잭션으로 저장한 뒤 응답합니다. 푸시 전송은 Redis Streams를 통해 비동기로 처리해, 외부 푸시 서비스의 지연이 결제 응답에 영향을 주지 않도록 구성했습니다.

백엔드가 알림 작업을 Redis Streams에 등록하면, 발송 작업이 알림을 읽어 Firebase Cloud Messaging으로 전송합니다. 전송 결과를 DB에 기록하고, 전송에 성공한 알림은 큐에 처리 완료로 표시합니다.
